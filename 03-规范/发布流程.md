# 发布流程设计

> 版本：v0.3（2026-10-30）｜ 状态：设计稿
> 目标：四个平台（公众号 / 知乎 / 小红书 / 今日头条）每天定时发布，
> 失败可追溯、可人工干预、不重复发、成本可控。
>
> **v0.3 主要变更：双队列合并为单队列。** 原「队列 A（三平台从第 8 关）+ 队列 B（头条从第 1 关）」
> 已废弃，改为一条队列按关号推进，第 N 关四平台发同一篇，谁缺补谁。
> 执行细节见 `AGENTS.md`，本文件只管设计取舍。

---

## 零、一句话

**内容由 AI 批量生成 → 去 AI 味 → 四平台适配 → 质检 → 定时任务在 12:00 立即发布 → 失败报给人。**

**v0.3 修正**：原先设想"晚上提前上传、用平台定时发布、0 点自动出街"，实测行不通——
头条加入合集后**不能用定时发布**（见 2.1.2）。所以改成**调度时间直接定在 12:00、脚本立即发布**。
本机不再需要半夜或 21:00 开机，只需要 12:00 那一会儿开机。

## 一、边界：什么能自动，什么不能

先把话说死，避免后面反复。

| 能全自动 | 只能半自动 | 永远需要人 |
|---|---|---|
| 内容读取、去 AI 味、平台改写、质检、状态记账、日志、失败报告 | 上传正文/图片、点击发布（浏览器自动化，可能断） | 扫码登录、过验证码、平台改版后修选择器 |

**"每天全自动、零人为"做不到。** 三个断点必然发生：登录态过期（公众号几天到几周，不可控）、验证码、平台改版。

可达到的目标：**日常零操作，每月约 2–4 次人工介入，每次 30 秒**（扫个码）。

## 二、四平台能力矩阵

按你的要求"优先官方 API"，逐个交代：

| 平台 | 官方发布 API | 现状 | 采用路径 | 平台自带定时发布 |
|---|---|---|---|---|
| **公众号** | 无（个人主体订阅号无法认证，`draft/add` 返回 48001） | 已确认 | 浏览器自动化 | 有（定时群发，占当天群发次数） |
| **今日头条** | 无公开接口 | 已确认 | 浏览器自动化（有现成 skill 可复用） | 有 |
| **知乎** | 无对外接口 | 已确认 | 浏览器自动化 | 无 |
| **小红书** | 无 | 已确认 | 浏览器自动化（风控最严） | 有 |

> **结论：四个平台全部只能浏览器自动化，没有一条官方 API 可走。**
> 好处是架构反而统一——一套 Playwright 框架 + 四个平台适配器，不用为某一家单独写 API 客户端。

~~**关键设计：能用平台自带定时发布的，就不要本机 0 点跑。**~~
**这条已被实测推翻，见 2.1.2。** 头条的合集与定时发布互斥，而合集是这个系列的核心，
所以最终放弃平台定时，改用"调度时间即发布时刻"。

### 2.1 单队列 + 只向前对齐（2026-10-30 改）

**v0.2 的双队列已废弃。** 原来四平台不在同一条进度线上（三平台从第 8 关续、头条从第 1 关起），
每天要处理两篇不同文章。实测发现这带来三个多余问题：队列边界容易算错、台账要维护两套游标、
"今天发哪篇"要看两处。合并成一条后这些全部消失。

| 项 | 值 |
|---|---|
| 队列数量 | **1 条** |
| 起点 | **第 9 关**（2026-10-30 定） |
| 推进方式 | 按关号，第 N 关四平台发**同一篇内容** |
| 已发过的平台 | 自动跳过，只补缺的 |
| 起点之前的空缺 | **不进队列**，归人工补发 |
| 每天篇数 | 1 篇（四平台同一篇） |

**执行顺序**：今日头条 → 公众号 → 知乎 → 小红书。头条最稳放最前（出问题最早暴露），
小红书风控最严放最后（避免它的风控波及后面的平台）。

**为什么单队列更安全**：按关号推进天然幂等。同一关重跑只会补没发的平台，
所以"失败即停"不会死锁，第二天自动接上，也不会重复发。

### 2.1.0 补发归人（2026-10-30 定）

**这是本版最重要的一条职责划分：机器管当天，人管历史。**

起点之前的空缺，`pub_ledger.pending()` 直接排除，`pub_daily.py` 永远不碰；
台账里这些位置的状态是 **「自补」**，与「待发」明确区分。

| 项 | 机器 | 人 |
|---|---|---|
| 第 9 关及之后 | ✅ 四平台自动发 | — |
| 第 1–8 关的空缺 | ❌ 不碰 | ✅ 手动补发 |

当前人工补发项共 **9 篇**：公众号第 1、6、8 关；今日头条第 1、2、5、6、7、8 关。
（知乎、小红书第 1–8 关已发完，无缺口。）

**为什么不交给机器补**，两条路都不可行：

| 补发做法 | 后果 |
|---|---|
| 一次补好几篇 | 短时间内高频发布，等于主动触发风控 |
| 把队首钉在第 1 关慢慢补 | 四个平台永远无法同步推进，"今天发第 N 关"这条规则失效 |

拆开之后职责清楚，两个目标（历史完整 / 当天对齐）互不干扰。

**代价**：台账会出现"某平台已发 2 篇、某平台已发 8 篇"的长期不对称。这是事实的反映，不是 bug，
**不要为了让数字好看去动 `起点`**——起点是"从哪天开始正常日更"的分界线，改它队列就倒回去了。

**终止条件**：第 100 关四平台全部发完即结束。不做回头重发。

### 2.1.1 头条落地状态（2026-10-30）

**已跑通，合集「逻辑闯关：100 道经典逻辑谜题」已建。** 实测有三条与预判不同的地方：

1. **没做实名认证也能发文章。** 后台顶部一直挂着「请完善账号信息，解锁发布文章、视频等权益功能」，
   点进去是大陆身份证 + App 扫码的实名流程，但发布编辑器正常可用、文章也正常进审核。
   所以这道横幅**不是发布的前置条件**，只影响部分权益。别被它卡住。
2. **合集标题下限是 5 个字。** 「逻辑闯关」4 个字填不进去，实际建的是
   「逻辑闯关：100 道经典逻辑谜题」（16 字，含主题关键词，对推荐更友好）。
3. **头条的「合集」是发布时挂上去的**，不像知乎要发完再收录。所以顺序是
   先建合集 → 发布时「添加至合集」→ 文章自动进合集，不用二次补录。

另外两处平台默认值要主动改掉：**「同时发布微头条」默认勾选**（会多一条重复内容），
**发完会弹「作品同步授权」**（勾了会把作品同步到懂车帝、住小帮，且网页端关不掉，只能去 App 关）。

**实际执行时间：12:00，立即发布。** 原计划"21:00 提前上传 + 平台定时发布"因 2.1.2 的硬限制作废。

### 2.1.2 头条的硬限制：合集与定时发布互斥（2026-10-30 实测）

编辑页底部三个按钮：`预览` / `定时发布` / `预览并发布`。**「定时发布」不是想用就能用。**

> 设好标题、正文、封面、合集后点「定时发布」，页面提示**「加入合集的文章无法选择定时发布」**，
> 时间选择器根本不弹。

| 想要 | 代价 |
|---|---|
| 进合集（系列必须） | 只能**立即发布**，不能用平台定时 |
| 用平台定时发布 | 必须**不加合集**，文章散落，没有系列入口 |

**决定：走「立即发布 + 进合集」，用调度时间（12:00）控制发布时刻。**

理由：100 关必须进合集，否则没有系列入口；而"先定时发出去、再手动改文章加合集"会重新触发审核，
更不稳定，也未验证。所以 B 方案（定时 + 后补合集）和 C 方案（等权益）都不再考虑。

如果以后头条放开这个限制，用 `node pub_tt_publish.js N --probe-schedule` 复测再评估。

**探测方法留个记录**：这个提示只闪 2–3 秒，截图和 dump 都抓不到。
最终是靠"点完按钮后每 1 秒抓一次页面文字、比对变化"才捕获到的。
以后遇到"点了没反应"的按钮，用同样的文本轮询，不要靠截图。

### 2.2 公众号：用「发表」，不用「群发」

公众号后台有两个按钮，很多人以为是一回事，其实是两条完全不同的路：

| | 群发 | 发表 |
|---|---|---|
| 推送到粉丝消息列表 | 是 | **否** |
| 次数限制 | 订阅号每天 1 次 | **不限次，不占群发次数** |
| 粉丝怎么看到 | 直接收到 | 进公众号主页，或搜标题/关键词 |

**决定：日常全部走「发表」。**

三个理由：
1. 日更账号天天群发必掉粉——没人想每天被推一次
2. 不限次，多篇也不会撞上限，彻底绕开这个问题
3. 账号定位本来就是"作者懒，不定期更新"，静默发表反而更贴

**代价要说清楚**：粉丝收不到任何提醒，打开率完全靠搜索、主页和转发。
公众号最大的价值本来是推送触达，放弃它等于放弃一部分流量。

**补救很简单**：哪天真想推，手动点一次群发就行，不用改流程、不用改代码。

### 2.3 AI 内容主动标注

**决定：主动标注。**

2026 年《人工智能生成合成内容标识办法》已落地，头条从年初起强制打标、小红书要求标注。
不标注一旦被识别，惩罚是限流降权甚至封号；主动标注只是流量打折。
两害相权，标注划算。

| 平台 | 怎么标 |
|---|---|
| 今日头条 | 发布页勾选「AI 生成」 |
| 小红书 | 内容声明里注明 |
| 公众号 / 知乎 | 文末加一行「本文由 AI 辅助整理」 |

这一步在「处理」模块里完成——随正文一起写进物料包，发布时不需要额外操作，
也不会因为漏勾而前功尽弃。

## 三、五个模块

每个模块独立可跑、独立重试、独立失败，互不阻塞。

### 3.1 采集 ingest

| 项 | 内容 |
|---|---|
| 输入 | `01-内容/<合集>/*.md`（AI 已生成、已定稿的母稿） |
| 输出 | `articles` 表新增记录，状态 `待处理`；正文快照存库（防母稿被改） |
| 执行条件 | 文件 H1 存在、字数 ≥ 800、未在库中（按文件内容 hash 去重） |
| 超时 | 单篇 5 秒 |
| 重试 | 文件读失败重试 2 次 |
| 错误处理 | H1 缺失/字数不足 → 状态 `内容不合格`，跳过，进早间报告 |
| 幂等 | 按 `content_hash` 唯一索引，重复跑不会重复入库 |

### 3.2 处理 process

| 项 | 内容 |
|---|---|
| 输入 | `articles` 表里状态 `待处理` 的记录 |
| 输出 | `variants` 表：一篇 × 四平台 = 4 条变体（标题、正文 HTML、标签、封面路径） |
| 执行条件 | 文章状态为 `待处理` |
| 超时 | 单篇 180 秒（含 1 次大模型调用） |
| 重试 | 大模型超时重试 2 次，指数退避（30s / 90s） |
| 错误处理 | 三次失败 → 状态 `处理失败`，进早间报告，不影响其他篇 |
| 复用 | `humanizer-zh` skill（去 AI 味）、`pub_md2html.py`（HTML）、`mk_xhs_note.py`（小红书文档）、`make_covers_wx.py` + `make_xhs_covers.py`（封面） |

**标题与封面（2026-10-30 定：保留关卡编号）**

原先计划删掉"第N关"，现在**撤销，标题和封面都保持原样**。

| 项 | 处理 |
|---|---|
| 标题 | 保留 `第41关｜辛普森悖论：…`，不改 |
| 公众号封面 | 1280×792，现有 100 张已齐（81–100 于 2026-10-30 补齐） |
| **知乎封面** | **直接复用公众号那张 1280×792**，不另出图 |
| 小红书封面 | 1080×1440 竖版，现有 100 张已齐 |
| 文件名 | 保留关号，内部主键 |
| 正文 | 本来就不含关号（已核实 100 篇） |

**去 AI 味照做**：标题不动，但正文仍过一遍 `humanizer-zh`。
这是唯一能对抗平台 AI 检测的抓手——头条 2026 年起强制打标、小红书跑 AI 率检测。

**四平台标题长度**（2026-10-30 按发布页占位符/计数器实测，不是听说）：

| 平台 | 硬上限 | 依据 | 处理方式 |
|---|---|---|---|
| 今日头条 | **2–30 字** | 占位符「请输入文章标题（2～30个字）」 | 结果前置，保留关号（"第1关｜两组都赢，合起来却输了"） |
| 知乎 | **100 字** | 占位符「请输入标题（最多 100 个字）」 | 原样，仅在超长时压钩子 |
| 公众号 | **64 字** | 编辑器计数器 `0/64` | 原样（22 字内最佳是经验值，不是限制） |
| 小红书 | **64 字** | 输入框 `maxlength=64` | 谜题名 + 短钩子 |

> **纠正一条旧错误**：v0.2 把知乎上限记成 16 字，导致 `zhTitle()` 在第 16 个字硬切，
> 出现"怎样找到宝"这种断词标题。16 字是**信息流里的显示截断**，不是输入限制。
> 代码已改为 100 字，并加了 `cutHook()` 在标点处断开，不再从词中间切。

### 3.3 审核 review

| 项 | 内容 |
|---|---|
| 输入 | `variants` 表状态 `待审核` |
| 输出 | 状态改为 `待发布` 或 `需修改`（附原因） |
| 执行条件 | 四条变体齐全 |
| 检查项 | ① AI 味残留（连接词密度、三段式、破折号）② 各平台字数上限 ③ 敏感词 ④ 标题是否含关号 ⑤ 封面/文档文件是否存在 |
| 超时 | 单篇 60 秒 |
| 重试 | 不重试（判定类任务重试无意义） |
| 错误处理 | 不通过 → `需修改`，写原因，进早间报告；**不阻塞其他篇** |

这一关是**对抗平台 AI 检测的唯一抓手**。头条 2026 年起强制 AI 打标、小红书跑 AI 率检测，不加工就是等着被降权。

### 3.4 发布 publish

| 项 | 内容 |
|---|---|
| 输入 | `variants` 表状态 `待发布` |
| 输出 | 各平台状态 `已发布`（含链接）/ `待人工`（含失败原因 + 截图路径） |
| 执行条件 | 审核通过 **且** 该（文章, 平台）组合未发过（防重复） |
| 超时 | 单平台 300 秒 |
| 重试 | **按错误类型分**，见第六节 |
| 错误处理 | 失败写 `publish_log`，不中断其他平台 |
| 隔离 | 一个平台失败不影响其他三个（四个适配器互相独立） |

**公众号适配器与其他三个不同**：点的是「发表」不是「群发」。
所以它**没有每日次数限制**，也不该出现"额度用尽"这个错误类型。
发表后拿到的是永久链接（可用于菜单、自动回复、文内引用），但没有推送记录。

### 3.5 通知 notify

| 项 | 内容 |
|---|---|
| 输入 | `publish_log` 当日记录 |
| 输出 | 一份早间报告（成功几篇、失败几篇、每个失败的具体原因和处理建议） |
| 执行条件 | 每天 08:00 固定触发，无内容也报"今日无任务" |
| 超时 | 30 秒 |
| 重试 | 不重试 |

报告长这样：

```
10-30 发布结果
✅ 成功 2/4
  公众号  已发  链接
  头条    已发  链接
❌ 失败 2/4
  知乎    登录态失效 —— 需重新扫码（预计 30 秒）
  小红书  触发验证码 —— 需人工过一次滑块
```

**"哪里失败、怎么修"必须写进报告**，这是你早上起来唯一要看的东西。

## 四、状态存储

用 **SQLite**（Python 标准库，零依赖，单文件），不用 JSON——台账 JSON 在并发/重试下会写坏。

| 表 | 关键字段 | 作用 |
|---|---|---|
| `articles` | id, 关号, 标题, content_hash(唯一), 状态, 入库时间 | 防重复入库 |
| `variants` | article_id, platform, 标题, 正文路径, 状态, 重试次数, 最后错误 | 一篇文章 × 四平台 |
| `platform_cursor` | platform, next_num, 更新时间 | ~~每个平台独立的待发游标~~ **单队列 + 单一全局起点后已不需要**：队首由「关号 ≥ 起点 且存在待发平台」直接算出 |
| `publish_log` | variant_id, 尝试时间, 结果, 错误类型, 截图路径 | 每次尝试都留痕 |
| `runs` | run_id, 开始/结束时间, 触发方式 | 一次批处理一行 |

**防重复发布**靠两层：
1. `variants` 表 `(article_id, platform)` 唯一索引 + 状态机（只有 `待发布` 能进 `已发布`）
2. 发布前查该平台当日是否已有成功记录

> 现有 `pub_ledger.py` 的 JSON 台账**升级**为这张 SQLite，不并存两套。

**当前实际状态（2026-10-30）**：仍在用 JSON 台账 `06-存档/_发布台账/<合集>.json`，SQLite 未落地。
原因是单线程、一天一篇、串行执行，JSON 的并发风险在这个场景下不存在。
`pub_daily.py` 每次只写一行、写完即落盘，够用。
**什么时候该升级**：如果将来要做多平台并发、或补发历史文章，再迁 SQLite——那时才有写坏的可能。

单队列下的台账结构（状态共四种：待发 / 已发 / 跳过 / 自补）：

```json
{
  "起点": 9,
  "记录": {
    "1": { "今日头条": {"状态": "自补"}, "公众号": {"状态": "自补"},
           "知乎": {"状态": "已发"}, "小红书": {"状态": "已发"} },
    "9": { "今日头条": {"状态": "待发"}, "公众号": {"状态": "待发"},
           "知乎": {"状态": "待发"}, "小红书": {"状态": "待发"} }
  }
}
```

队首 = 第一个"**关号 ≥ 起点** 且至少一个平台还是待发"的关号。已发的平台自动跳过，
「自补」和「跳过」都不进队列。

## 五、调度与重启

| 项 | 设计 |
|---|---|
| 调度机制 | WorkBuddy 定时任务，**每天 12:00 跑一次 `pub_daily.py`**，四平台同一篇，立即发布 |
| 为什么是 12:00 | 头条合集不能用定时发布（2.1.2），只能用调度时间控制发布时刻 |
| 为什么不是 0 点 | 中午 12:00 阅读量高于凌晨；且这个时点用户大概率开机，能处理登录态过期 |
| 系统重启后能否继续 | **能**。定时任务由服务端调度，不依赖本机常驻进程；但**本机必须开机**才能执行 |
| 本机没开机怎么办 | 当天任务记为 `未执行`，次日跑时队首仍是同一关，自然补上，不会漏 |
| 幂等 | 台账按（关号, 平台）记状态，重复触发只处理 `待发`，不会重发 |

**唯一成本：12:00 那台电脑必须开着。** 这是"放弃平台定时发布"换来的代价，接手的人要跟用户确认，不要默认假设。

## 六、失败分类与处理

**v0.3 修正：发布类操作一律不重试。** v0.2 写过"网络超时重试 3 次"，这条撤掉了。

原因：网络超时发生在**点击发布之后**时，你并不知道文章到底发出去了没有。
重试的后果不是"多试一次"，而是**重复发一篇**——而重复的两篇会同时挂在账号上，观感直接崩。
一天一篇的节奏下，"今天没发"成本极低，"今天发了两遍"成本很高。所以宁可不发。

| 错误类型 | 典型表现 | 处理 | 是否重试 |
|---|---|---|---|
| 网络/超时 | 页面加载失败、脚本 900 秒未结束 | 标记失败，**不重试**。明天队首仍是这一关，自然补上 | ❌ |
| 登录态失效 | 跳转登录页、二维码页 | 标记 `待人工`，报"需要扫码" | ❌ |
| 验证码/滑块 | 出现验证组件 | 标记 `待人工`，**当天停手** | ❌ |
| 选择器失效 | 找不到标题输入框 | 标记 `待人工` + 截图，报"平台可能改版" | ❌ |
| 内容被拒 | 平台提示违规/重复 | 标记 `需修改`，附平台原话 | ❌ |
| 线上查重命中 | 头条已有该关 | **跳过该平台**，继续下一个平台 | ❌（跳过≠重试） |

失败一律截图存档（`06-存档/_运行截图/`），看图就知道卡在哪。

**唯一例外**：查重命中时跳过头条、继续发其他平台，这不是重试，是正常分支。

## 七、成本评估

**每天一篇**（单队列，四平台同一篇），不是两篇。

| 项目 | 次数/天 | 估算 Token |
|---|---|---|
| 去 AI 味 + 平台改写（四平台规则写进一个 prompt，不按平台重复传全文） | 1 | 输入 ~6k / 输出 ~8k |
| 质检（只传标题 + 抽样段落） | 1 | ~3k |
| 失败诊断（视觉模型看图，仅失败时） | 0–1 | ~1k/次 |
| **合计** | 约 2–3 次 | **约 10k token/天，30 万/月** |

按当前主流模型价格，**每月成本在十元以内**，可忽略。

真正的时间成本在浏览器自动化（每平台 1–3 分钟），不在模型。**四平台 = 每天 4 次上传操作**，
12:00 那轮大概要跑 6–12 分钟。这是每天唯一需要电脑开着的时段。

**省钱要点**：四平台改写合并成一次调用（把四个平台的规则写进一个 prompt），不要一篇调四次。

## 八、落地顺序

按"风险从低到高、验证从易到难"排，每步都能独立回滚：

| 阶段 | 内容 | 验证标准 | 状态 |
|---|---|---|---|
| **0** | 产物齐备：公众号封面 81–100 已补齐（2026-10-30），小红书封面 100 张已齐；跑一遍文档版 | 100 关 × 3 类产物无缺口 | ✅ 完成 |
| **1** | 状态台账 + 体检模块（不发布） | 100 篇体检 blocker 0 | ✅ 完成（用 JSON 台账，未上 SQLite） |
| **2** | 接**今日头条**（风控最宽松，先跑通） | 连续 3 天自动发成功 | ⚠️ 部分（已发第 3、4 关，但第 1、2 关丢失，见 AGENTS.md 事故记录） |
| **3** | 接**公众号**（走「发表」；验证登录态断点恢复） | 至少经历 1 次登录态过期并恢复 | ⏳ 脚本已写，未经 `pub_daily.py` 端到端跑过 |
| **4** | 接**知乎** | 连续 3 天成功 | ⏳ 同上 |
| **5** | 接**小红书**（风控最严，单独灰度） | 连续 5 天无异常 | ⏳ 同上 |

**v0.3 修正**：原阶段 2/3 的"队列切换"说明已作废——单队列下没有切换，四个平台按固定顺序串行执行。
但**上线节奏仍然要一个一个来**：第一次出问题时要能立刻判断是哪个平台的适配器坏了。

`pub_daily.py` 已支持 `--平台 <名字>` 只跑单个平台，用于逐平台验证。
**验证完必须回到不带 `--平台` 的统一模式**，否则队列会歪。

**不要跳步。** 四个平台同时首次上线，第一次失败你分不清是自检、查重、还是某个平台的选择器。
